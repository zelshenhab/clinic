# Интеграция мобильного приложения клиники с 1С:БИТ.Управление медицинским центром

Черновик архитектуры для совместного обследования. Версия от 26.10.2026.

## 1. Участники и роли систем

| Система | Что это | Роль в интеграции |
|---|---|---|
| **БИТ.УМЦ (1С)** | МИС клиники: расписание, записи, клиенты, номенклатура, медицинские документы | **Ведущая система (master)** для расписания, записей, клиентов, услуг и цен |
| **Наш API-сервер** (Node.js) | Бэкенд мобильного приложения | Единственная точка обращения к 1С; кэш справочников, сопоставление идентификаторов, очередь повторов |
| **Наша БД** (PostgreSQL/Supabase) | Данные приложения | Учётная запись пациента (вход по SMS), родственники, уведомления, копии записей с УИД 1С |
| **Мобильное приложение** (Flutter, iOS/Android) | Канал пациента | Никогда не обращается к 1С напрямую, только к нашему API |

Принцип: **запись считается созданной только после того, как 1С вернула УИД.** Если 1С недоступна, приложение сообщает об ошибке и не создаёт «локальных» записей. Так исключаются двойные бронирования.

```
Пациент ──► Мобильное приложение ──HTTPS──► Наш API ──HTTPS (hs/bwi, Key)──► БИТ.УМЦ
                                              ▲                                 │
                                              └──── события из 1С (доработка) ──┘
```

## 2. Потоки данных

Легенда: **✅ типовой метод** — есть в документации «Описание форматов веб-сервисов и файлов» (06.02.2025), HTTP-сервисы `hs/bwi`. **🛠 доработка** — в типовой версии отсутствует, требуется оценка со стороны 1С.

### 2.1. Справочники (1С → приложение)

| Данные | Метод | Частота | Комментарий |
|---|---|---|---|
| Филиалы | ✅ `DictionaryData` / `GetListClinic` | раз в сутки + по кнопке | Нужны также адрес, телефон, часовой пояс, режим работы → 🛠 (сейчас только `Наименование`, `УИД`) |
| Врачи | ✅ `DictionaryData` / `GetListEmployees` | каждые 15–60 мин | Есть ФИО, специализация, организация, основные услуги. Для карточки врача в приложении нужны фото, стаж, описание, признак «показывать на сайте» → 🛠 или ведём на нашей стороне |
| Услуги и цены | ✅ `DictionaryData` / `GetNomenclatureAndPrices` | каждые 15–60 мин | Параметр `Clinic` игнорируется. Нужны цены по филиалу, если они различаются, и полная связь «врач ↔ услуга» (сейчас только `ОсновныеУслуги`) → 🛠 |

Приложение показывает только то, что разрешено фильтром «Настройки обмена с сайтом» в 1С.

### 2.2. Расписание и свободное время (1С → приложение)

| Задача | Метод | Режим |
|---|---|---|
| Свободное время врача на выбранную дату | ✅ `Schedule`, `Method=GetSchedule20`, `OnlyFreeTime=true`, `Employees`, `Clinic` | Онлайн при открытии экрана записи; кэш 30–60 сек |
| Поиск «ближайшее свободное время» на 14 дней | ✅ `Schedule`, `GetSchedule20` по нескольким врачам или `GetEnlargementSchedule` | Фоновая выгрузка, например каждые 5–15 мин |

Наш сервер нарезает свободные периоды (`ПериодГрафика`: `Дата`, `ВремяНачала`, `ВремяОкончания`) на слоты по длительности услуги (`Продолжительность`) или по `ДлительностьПриема` врача. Перед записью свободное время перепроверяется в 1С.

Время в ответах 1С приходит **без часового пояса** (`2024-10-11T09:00:00`), а в запросах передаётся в формате `ДД.ММ.ГГГГ ЧЧ:ММ:СС`. Мы трактуем его как местное время филиала. Часовой пояс каждого филиала нужно согласовать.

### 2.3. Запись на приём (приложение → 1С)

Рекомендуемая схема — «с бронированием» (схема 1 из документации):

1. Пациент выбирает врача, услугу и время → наш API вызывает ✅ `Reservation` (бронь, УИД брони). Документация требует оформить запись в течение 15 минут.
2. Пациент подтверждает запись и выбирает, для кого она: для себя или для родственника.
3. Наш API вызывает ✅ `AppointmentCreate`, `Method=BookAnAppointmentWithParams` с полями:
   - `Clinic`, `EmployeeID`, `Service`, `Date`, `TimeBegin`, `DurationType=ServiceDuration`
   - `PatientSurname`, `PatientName`, `PatientFatherName`, `Birthday`, `Phone`, `Email`
   - `Comment`, например: «Запись из мобильного приложения, №<наш id>»
4. 1С возвращает `Ответ.Результат=true` и `Ответ.УИД`. Мы сохраняем УИД заявки и показываем пациенту «Запись создана».
5. Администратор видит заявку в 1С по ссылке «Новых внешних заявок». Дальнейшие действия выполняются по регламенту клиники.

Открытые вопросы и доработки:
- 🛠 **Идентификатор клиента.** Ответ содержит только УИД заявки. Нам нужен УИД найденного или созданного клиента, чтобы потом получать его записи и документы. Нужно либо вернуть `Client` в ответе, либо добавить метод поиска клиента по телефону, ФИО и дате рождения.
- 🛠 **Идемпотентность.** При обрыве связи после отправки запроса возможен дубль. Просим принимать наш внешний идентификатор, например в `Comment` или в отдельном поле, и возвращать уже созданную заявку при повторе.
- 🛠 **Запись ребёнка или родственника.** Пациент в заявке — родственник, телефон — владельца аккаунта. Нужно согласовать, как 1С ищет и создаёт такого клиента, и нужна ли связь с законным представителем.
- Как используется бронь `Reservation` в `AppointmentCreate`: снимается автоматически или нужно передавать её УИД?

### 2.4. Перенос и отмена (приложение → 1С)

| Действие | Метод | Комментарий |
|---|---|---|
| Перенос | ✅ `AppointmentCreate` с `GUID` существующей заявки и новым временем | Правило «не позднее чем за N часов» проверяется на нашей стороне и, при необходимости, в 1С |
| Отмена | ✅ `AppointmentCancel` (`GUID`, `Reason`, `AdditionalInformation`) | По документации причина отмены не попадает в отчёт «Анализ причин закрытия заявок». Нужна ли причина в отчётах? |

### 2.5. Статусы записей (1С → приложение)

- ✅ `AppointmentStatus` (`GUID`) возвращает код и описание. Например, `2` — «Обработана», `4` — «Не пришел». **🛠 Нужен полный перечень кодов.**
- Опрос по одной заявке не масштабируется. Предлагаем 🛠 один из вариантов:
  - **А (предпочтительно):** 1С отправляет HTTP-запрос на наш адрес при изменении записи: подтверждение, перенос, отмена клиникой, приход, завершение.
  - **Б:** метод 1С «изменения записей с момента X», который мы опрашиваем раз в 1–2 минуты.
- Сопоставление статусов: «Новая» → *ожидает подтверждения*; «Обработана» → *подтверждена*; «Отменена» → *отменена*; «Не пришел» → *неявка*; «Выполнена» → *завершена*. Уточняется при обследовании.

### 2.6. Записи, созданные в клинике (1С → приложение)

🛠 Пациент должен видеть в приложении и записи, оформленные администратором по телефону. Нужен метод «записи клиента» по УИД клиента за период (дата, время, врач, услуга, филиал, статус) или передача таких записей событиями (вариант А из п. 2.5).

### 2.7. Лист ожидания (приложение → 1С)

✅ `AppointmentCreate`, `Method=FastBookAnAppointment` (или `...WithClient`), с полями `Specialization`, `Comment` и контактами. Используется, когда на выбранный день нет свободного времени: «перезвоните мне».

### 2.8. Медицинские документы и результаты анализов (1С → приложение)

🛠 В типовой версии отсутствует. Предлагаемая схема:
- При проведении документа, например протокола осмотра или результата исследования, который клиника разрешает показывать пациенту, 1С отправляет на наш адрес: УИД клиента, УИД заявки или приёма, вид документа, название, дату, врача и **PDF-файл** (base64 или временную ссылку).
- Мы храним файл в закрытом хранилище и показываем его владельцу аккаунта и его родственникам. Пациент получает уведомление.
- Нужно согласовать: какие виды документов публикуются, подписываются ли они электронной подписью, требуется ли отдельное согласие пациента.

### 2.9. Онлайн-оплата

Вне первого этапа. Обсуждается отдельно: эквайринг и передача оплаты в 1С.

## 3. Техническая часть

**Публикация 1С.**
- Адрес вида `https://<адрес>/<BASE_NAME>/hs/bwi/<метод>`.
- Только HTTPS, доступ по белому списку IP нашего сервера.
- Минимальные релизы с HTTP-сервисами `bwi`: БИТ.УМЦ 2.0.49.54, БИТ.УМЦ КОРП 2.1.25.38.

**Аутентификация.**
- `Key` (ключ API из «Настроек обмена с сайтом») в теле каждого запроса.
- Дополнительно: пользователь 1С с минимальными правами для HTTP-публикации (Basic).
- Ключ хранится только на нашем сервере.

**Формат.** JSON, `POST`, UTF-8. Ошибка: `Ответ.Результат=false` + `Ответ.ОписаниеОшибки`.

**Наша сторона:**
- Таймаут 10 с, повтор безопасных запросов (чтение) с экспоненциальной задержкой.
- Создание записи **не повторяется вслепую**: до решения вопроса идемпотентности сначала проверяется статус.
- Журнал всех обменов без персональных данных в логах.
- Мониторинг доступности 1С.

**Входящие события из 1С** (для доработок 2.5 А, 2.6, 2.8):
- Наш адрес `POST https://<наш API>/api/v1/integrations/bit/events`.
- Подпись HMAC-SHA256 с общим секретом в заголовке, идентификатор события для защиты от повторов.
- Ответ `200` = принято. При ошибке 1С повторяет отправку.

**Сопоставление идентификаторов.** Мы храним соответствие наших id и УИД 1С для филиала, сотрудника, номенклатуры, клиента, заявки и листа ожидания.

**Персональные данные (152-ФЗ).** Передаются ФИО, телефон, e-mail и дата рождения пациента, а на этапе документов — медицинские сведения. До запуска нужно подтвердить размещение нашей БД и сервера в РФ и оформить поручение на обработку ПДн и договор между клиникой и исполнителем.
