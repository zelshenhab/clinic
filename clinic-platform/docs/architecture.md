# Architecture decisions

- Shared monorepo packages define Zod API contracts; Node uses strict TypeScript and Express 5. React uses JavaScript/Vite and TanStack Query. Flutter uses feature-level data/domain/presentation separation and Cubit state.
- Supabase SDK/PostgREST is the database access layer, avoiding a second ORM schema and preserving SQL migrations as the schema authority. Server-only service-role access requires explicit API authorization before every private operation.
- Doctors have a global identity and clinic-specific assignments, specialties, services, and schedules. Composite foreign keys enforce all tenant relationships. Overlapping active appointments for the same doctor are prohibited globally, including across clinics.
- Authentication identities stay in auth.users; patient profiles and staff memberships are separate. Supabase getUser performs remote token validation; clinic-role checks use stored memberships rather than client claims. No development authentication bypass exists.
- RLS is default deny, client mutations have no grants, and medical records are not available to clients. Patient-owned appointments and authorized staff appointment rows can be read by Realtime. Doctor access is limited to their own assigned appointments.
- Clinic switching must cancel requests, erase scoped query data, reset navigation, and unsubscribe previous Realtime channels. ClinicCubit and ClinicScope now implement persisted UUID selection, cancellation, registered state reset and stale-response rejection; route reconstruction prevents old clinic content from remaining visible. The dashboard implements the same lifecycle through ClinicContext, scoped query keys and channel cleanup.
- The dashboard subscribes with a user JWT to private staff:clinic:user channels. SQL emits only identifiers to currently authorized recipients; clients deduplicate, refetch through the API and invalidate after reconnects. Logout, role changes and clinic switches clean up subscriptions. The Flutter patient consumer remains pending.
- Staff and patient booking share SQL slot validation and one atomic booking transaction. It validates duration, local timezone, schedules, breaks, exceptions, membership and current service price, then records the appointment, immutable price snapshot, status history and audit. Clinic and doctor advisory locks coordinate settings/schedule changes; the global doctor exclusion constraint provides a final overlap guard. Realtime events are emitted by the appointment trigger.
- Exceptions use stable codes and sanitized messages. Request IDs appear in responses and structured logs. Logs do not include headers, bodies, phone numbers, JWTs, medical content, or raw database errors.

Phase 2 uses Supabase Flutter with a secure LocalStorage implementation, automatic SDK refresh, refresh-stream handling, and a single-retry Dio interceptor. Phone auth happens through Supabase; business data stays behind Node authorization. Flutter domain layers use a plain Dart cancellation signal rather than depending on Dio.

The React dashboard uses feature routes, lazy loading, React Hook Form/Zod, Luxon and TanStack Query. Authentication restores Supabase sessions, validates staff access through Node, refreshes one failed authorized request and clears scoped data on expiry. Role-aware navigation improves usability; Node and server-only SQL functions enforce authorization independently.

Catalog deactivation preserves appointment history. Doctor identity is global, while professional presentation and assignments are clinic-specific. Calendar geometry is presentation only; SQL remains authoritative for availability. Revenue-style statistics are explicitly labeled completed appointment value, derived from stored price snapshots rather than accounting payments.
