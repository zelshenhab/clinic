# Patient booking tools, schedule shortcuts and arrival queue

Apply `supabase/migrations/202610160010_patient_experience.sql` once in the Supabase SQL Editor, after migrations 001–009. This is incremental SQL; do not rerun the initial setup or reset patient data. Restart `npm run dev:api`, refresh the dashboard and rebuild Flutter with `flutter run --dart-define-from-file=config/local.json`. Docker is not required. This migration has been exercised locally with PostgreSQL/PGlite; it has not been applied to the hosted project by this change.

## Where to use the features

- **Clinic settings → Cancellation and rescheduling policy**: administrators set minimum notice in minutes, separately for cancellation and rescheduling (default 120, range 0–10080). Patients see the applicable notice when confirming a change. The backend rechecks it atomically; 0 permits changes only before the appointment starts. Reception can still assist through its authorized staff workflow.
- **Flutter → My appointments**: future pending/confirmed appointments that have not arrived show Cancel and Reschedule. Rescheduling selects a current public slot for the same doctor/service, preserves the original price snapshot, submits an optimistic version and updates the list only after a committed response. Existing bookings and cross-clinic doctor overlap remain protected. Expired notice, stale records and occupied slots produce an error, never a false success.
- **Flutter → booking with no available times**: a signed-in patient with a complete profile can join that doctor's service/day waitlist. **My appointments → My waitlist** lists the latest 50 requests with doctor/service labels, state and leave action. A notification offers a chance to book; it does not reserve or automatically book a slot. Rejoining after a later closure creates a new notification generation. Multiple patients can receive an offer and the first successful atomic booking wins.
- **My schedule → Schedule tools**: the doctor copies the effective capacity of a source week into a future target week, or blocks a full day/vacation interval. Weeks normalize to Monday in the clinic timezone. Weekly shifts, breaks and open/closed exceptions contribute to copied capacity; patient bookings are never copied. Existing active appointments in the target period are protected. Other weeks' exceptions are retained; the result is bounded to 400 exceptions. The hourly editor still controls all 24 hours.
- **Arrival queue**: choose a clinic-local day. Reception moves confirmed appointments from Scheduled → Arrived → Waiting. The assigned doctor moves Arrived/Waiting → In consultation → Finished, after the scheduled start. Finishing also completes the appointment. Administrators can perform both sets of actions. Click a patient to open appointment details, including the existing confirmation workflow for pending appointments. Queue data is bounded to 100 records with an explicit truncation notice. Doctors see their own queue even when calling an admin URL. All attendance transitions use a version, history and audit record.
- **Flutter → Home → Find the nearest appointment**: public search with a specialty filter, doctor/service names, prices and clinic-local times. Searches at most 14 days and 200 doctor/service combinations per day; a cap notice asks the patient to narrow the filter. Selecting a result opens booking on its correct clinic-local day. Actual booking revalidates availability.

## Notifications and reminders

Notifications are durable database records. Booking creation, confirmation, cancellation and rescheduling create a patient-owned notice in the same transaction. Flutter Notifications shows the localized notice, links to appointments or the waitlist and supports marking it read.

The API starts a worker immediately and then once per minute. Its database transaction uses an advisory lease and unique event keys, making retries and multiple API processes safe. It creates 24-hour and 1-hour reminders only when the appointment was created early enough for that threshold. If catching up inside the last hour it sends the 1-hour reminder, rather than both reminders together. Cancelled/completed appointments do not receive new reminders. A changed start time gets a distinct reminder key. Notifications already delivered remain historical and direct the patient to current appointment details.

Waitlist checks rotate by last-check time, process at most 100 entries per run and notify only when the current shared availability function finds a slot. Reminder batches process at most 500 appointments that have due, undelivered work. Under heavy load batches may take additional cycles. The API needs to be running for timed jobs; restarting catches up still-relevant due work. The worker has a 15-second transport deadline and retries on the next interval without logging patient contents or secrets.

**Delivery implemented here is inside the app.** No APNs/FCM background push, SMS, email or WhatsApp delivery is configured or claimed. Opening the app fetches the durable notices even if it was closed at the time. A separate delivery-provider integration is required for notifications on a locked phone.

Private `patient:clinic:user` broadcasts contain only event/clinic/record identifiers. The mobile appointment and notification lists subscribe to that private channel, debounce updates and refresh on reconnect, with a 30-second fallback. Scope reset/logout cancels subscriptions/timers and discards stale responses. Public availability broadcasts continue to contain no patient or appointment identifiers. Dashboard queues use the existing private clinic staff updates and fallback refresh.
